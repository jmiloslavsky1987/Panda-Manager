# Phase 84.1: discovery-scan-merge-update-flow — Research

**Researched:** 2026-05-04
**Domain:** Discovery pipeline — merge/update flow for entity enrichment
**Confidence:** HIGH

## Summary

Phase 84.1 adds a merge/update flow on top of Phase 84's discovery scan pipeline. Rather than always
creating new entities, approved items with an `entity_match` field should enrich existing entities.
The three entity types in scope are `team_engagement` sections, `workflow_step` entries, and
`arch_node` records. The phase also fixes the known `onConflictDoNothing()` bug on `arch_node`
approvals.

The current codebase already has full approve-route infrastructure, Drizzle ORM patterns,
`DiscoveryQueueItem` type, and `QueueItemRow` / `ReviewQueue` components in place.
All changes are additive: two new fields on the Claude prompt output, a new `action: "merge"` branch
in the approve route, a Merge button alongside Approve in `QueueItemRow`, and a DB-level fix for the
duplicate arch_node constraint.

**Primary recommendation:** Follow the existing switch-case pattern in `insertDiscoveredItem()`. Add
a parallel `mergeDiscoveredItem()` function triggered when the POST body carries `action: "merge"`.
Propagate `entity_match` and `suggested_position` through the `discoveryItems` table (or pass
directly in the approve POST body — see Trade-off section below). Fix the arch_node duplicate bug
as the first task so it cannot interfere with tests.

### Locked Decisions

- Claude returns `entity_match` (string, the existing entity label being enriched)
- For `workflow_step`, Claude also returns `suggested_position: { after: "Step label" }`
- ReviewQueue shows a "Merge" button alongside "Approve" for items with `entity_match` set
- Approve route gains `action: "merge"` branch per type:
  - `team_engagement`: append new text to existing section's `content` (newline-separated)
  - `workflow_step`: add step to existing workflow at `suggested_position` (default to last if not found)
  - `arch_node`: upsert existing node's `notes` (append style, not replace)
- Fix `arch_node` `onConflictDoNothing()` bug from Phase 84 verification

### Merge Semantics (Locked)
- `team_engagement`: `content` field of existing section gets new text appended (`\n` separator)
- `workflow_step`: new row inserted into workflow steps at computed order position; resolved by looking
  up the referenced step label and inserting after it (default to last if not found)
- `arch_node`: existing node's `notes` gets discovered text merged in (append style)

### Claude's Discretion
- Exact field transport mechanism: pass `entity_match` + `suggested_position` in the approve POST
  body vs storing them in the `discovery_items` table (see Architecture Patterns below — recommendation
  is POST body, no schema migration required)
- Exact text of "Merge" button / loading state copy
- Whether to add `entity_match` to `DiscoveryQueueItem` type or rely on a prop-drilled callback

### Deferred Ideas (OUT OF SCOPE)
- Merge flow for `action`, `risk`, `decision`, `milestone`, `stakeholder` types
- Conflict diff UI for merge (the existing `DiffView` component handles create-time conflicts; out of scope for 84.1 merge path)
- Undo merge

### Pattern 1: Prompt Template Extension

**What:** Extend `DISCOVERY_SYSTEM_TEMPLATE` to emit two new optional fields.
**When to use:** Claude must return entity_match alongside suggested_field when enrichment is detected.

```typescript
// Source: lib/discovery-scanner.ts (current DISCOVERY_SYSTEM_TEMPLATE)

   suggested_position: (optional, workflow_step only) { "after": "<step label>" } — where to insert the step`
```

Key constraint: `entity_match` and `suggested_position` are OPTIONAL in the Claude JSON output.
Items without `entity_match` continue through the existing "create" path.

### Pattern 2: Transport via POST Body (no schema migration)

**What:** Pass `entity_match` and `suggested_position` in the approve POST body from the UI.
**When to use:** Avoids adding new columns to `discovery_items` table and a DB migration.

```typescript
// Zod schema extension in approve/route.ts:
const ApproveRequestSchema = z.object({
  projectId: z.number(),
  itemIds: z.array(z.number()),
  action: z.enum(['approve', 'merge']).optional().default('approve'),
  entity_match: z.string().optional(),           // existing entity name for merge
  suggested_position: z.object({                  // workflow_step only
    after: z.string(),
  }).optional(),
});
```

The ReviewQueue reads `entity_match` from the queue item (already returned by `/api/discovery/queue`)
and passes it to the approve POST when the Merge button is clicked.

**Alternative:** Store `entity_match` + `suggested_position` as new columns in `discovery_items`.
This requires a DB migration (migration 0048 or similar) and is heavier for what is a display-time hint.
Recommendation: POST body transport. The data is ephemeral and is only needed at approval time.

### Pattern 3: mergeDiscoveredItem() Function

**What:** A parallel function to `insertDiscoveredItem()` that performs update-or-append operations.
**When to use:** When `action === 'merge'` in the POST body.

```typescript
// Source: pattern from approve/route.ts insertDiscoveredItem()
async function mergeDiscoveredItem(
  item: DiscoveryItem,
  entityMatch: string,
  suggestedPosition?: { after: string }
): Promise<void> {
  const field = item.suggested_field ?? 'history';
  const projectId = item.project_id;

  switch (field) {
    case 'team_engagement': {
      const [existing] = await db.select()
        .from(teamEngagementSections)
        .where(and(
          eq(teamEngagementSections.project_id, projectId),
          eq(teamEngagementSections.name, entityMatch)
        ));
      if (existing) {
        await db.update(teamEngagementSections)
          .set({ content: sql`${teamEngagementSections.content} || '\n' || ${item.content}` })
          .where(eq(teamEngagementSections.id, existing.id));
      }
      break;
    }
    case 'workflow_step': {
      const [workflow] = await db.select()
        .from(e2eWorkflows)
        .where(and(
          eq(e2eWorkflows.project_id, projectId),
          eq(e2eWorkflows.workflow_name, entityMatch)
        ));
      if (workflow) {
        let position = await resolveStepPosition(workflow.id, suggestedPosition?.after);
        await db.insert(workflowSteps).values({
          workflow_id: workflow.id,
          label: item.content,
          position,
        });
      }
      break;
    }
    case 'arch_node': {
      const [node] = await db.select()
        .from(archNodes)
        .where(and(
          eq(archNodes.project_id, projectId),
          eq(archNodes.name, entityMatch)
        ));
      if (node) {
        const merged = node.notes ? `${node.notes}\n${item.content}` : item.content;
        await db.update(archNodes)
          .set({ notes: merged })
          .where(eq(archNodes.id, node.id));
      }
      break;
    }
    default:
      // Non-merge types fall through to create path
      await insertDiscoveredItem(item);
  }
}
```

### Pattern 4: Step Position Resolution

**What:** Given a `workflow_id` and an optional `after` step label, compute the `position` integer for
the new step.

```typescript
async function resolveStepPosition(
  workflowId: number,
  afterLabel?: string
): Promise<number> {
  const existingSteps = await db.select({ id: workflowSteps.id, label: workflowSteps.label, position: workflowSteps.position })
    .from(workflowSteps)
    .where(eq(workflowSteps.workflow_id, workflowId));

  if (!afterLabel || existingSteps.length === 0) {
    // Default: insert at end
    const maxPos = existingSteps.reduce((m, s) => Math.max(m, s.position), 0);
    return maxPos + 1;
  }

  const anchor = existingSteps.find(s => s.label === afterLabel);
  if (!anchor) {
    // Anchor not found — default to last
    const maxPos = existingSteps.reduce((m, s) => Math.max(m, s.position), 0);
    return maxPos + 1;
  }

  // Insert after anchor: shift all steps with position > anchor.position up by 1, then use anchor.position + 1
  // IMPORTANT: non-contiguous position integers are fine — ordering by position ASC is the display contract
  return anchor.position + 1;
}
```

Note: `workflowSteps.position` is a plain integer — there is no unique constraint on it. Gaps in
the sequence are acceptable. Do NOT resequence existing steps; just insert at `anchor.position + 1`.

### Pattern 6: DiscoveryQueueItem Type Extension

```typescript
// components/QueueItemRow.tsx — extend DiscoveryQueueItem interface
export interface DiscoveryQueueItem {
  // ... existing fields ...
  entity_match?: string           // NEW: name of existing entity this should enrich
  suggested_position?: { after: string }  // NEW: workflow_step only
}
```

The `/api/discovery/queue` route returns rows from the `discovery_items` table. Since `entity_match`
is NOT stored in DB (Phase 84 design stores entity context only in Claude output, not in DB rows),
the queue API cannot return it. **This is the key architectural decision:**

- The `entity_match` value must come from Claude's JSON output at scan time
- It needs to survive until approval time
- **Resolution:** Store `entity_match` and `suggested_position` in `discovery_items.source_excerpt`
  column? No — that's already used. Better: add two new nullable text columns to `discovery_items`:
  `entity_match text` and `suggested_position text` (JSON string).

**Revised recommendation:** Add `entity_match` and `suggested_position` columns to `discovery_items`.
This is a simple additive migration (two nullable text columns). The scanner writes them during
scan/route.ts item storage. The queue API already returns all columns. The Merge button reads from the
returned queue item naturally.

### Anti-Patterns to Avoid
- **Resequencing workflow step positions:** Never UPDATE all existing steps to renumber them; just
  insert at `anchor.position + 1`. Display order only needs consistent `ORDER BY position ASC`.
- **Storing merged content before approval:** Merge should only happen in the approve route when
  the user explicitly clicks Merge. Do not pre-compute merges during scan.
- **Overwriting instead of appending:** The merge semantics are append-only. Use SQL string concat
  (`notes || '\n' || $newText`) or JS string concatenation — never a plain `.set({ notes: newText })`.
- **Skipping the onConflictDoNothing fix:** The arch_node bug must be fixed before writing merge
  logic, otherwise a second approval of the same node still throws a DB constraint error even
  through the non-merge path.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Text append in SQL | Custom string concat outside DB | `sql\`${col} || '\n' || ${val}\`` (Drizzle `sql` template) | Atomic, avoids race conditions on concurrent approvals |
| Position ordering | Resequence all existing steps | Insert at `max_pos + 1` or `anchor_pos + 1` | Non-destructive; position gaps are fine |
| Entity lookup by name | Fuzzy search | Exact `eq(name, entityMatch)` | `entity_match` comes directly from Claude using existing entity names in the prompt context |

## Common Pitfalls

### Pitfall 1: entity_match Not Stored in DB
**What goes wrong:** ReviewQueue fetches queue items from `/api/discovery/queue`. If `entity_match`
is only in the Claude JSON response (not persisted), the Merge button cannot be shown because the
queue item has no `entity_match` field.
**Why it happens:** The Phase 84 `discovery_items` table has no `entity_match` column. Claude emits
it in the JSON array, but `scan/route.ts` must explicitly store it when inserting the `discovery_item`.
**How to avoid:** Add `entity_match text` and `suggested_position text` (JSON) columns to
`discovery_items` via a DB migration. Update `scan/route.ts` to persist these fields.
**Warning signs:** Merge button never appears in ReviewQueue even after successful scan.

### Pitfall 2: arch_node Unique Constraint on Duplicate Approval
**What goes wrong:** Approving the same `arch_node` discovery item twice throws a PostgreSQL unique
constraint violation (`arch_nodes_project_track_name_idx` on `(project_id, track_id, name)`).
**Why it happens:** Phase 84's `approve/route.ts` arch_node case uses plain `.insert()` with no
conflict handling (the Phase 84 VERIFICATION.md documents this as a known bug, line 124).
**How to avoid:** Fix first — add `.onConflictDoNothing()` to the existing arch_node insert in
`insertDiscoveredItem()`. This is the bug fix in BUG-01.
**Warning signs:** 500 error in the approve response `errors[]` array for arch_node items on second approval.

### Pitfall 3: Workflow Step Position Collision
**What goes wrong:** Two steps inserted at the same `position` value. Display order becomes
non-deterministic.
**Why it happens:** `anchor.position + 1` may already be occupied by another step if steps were
inserted non-sequentially.
**How to avoid:** This is acceptable by design — `workflowSteps.position` has no unique constraint.
Display order is `ORDER BY position ASC, id ASC` (id as tiebreaker). Document this contract in code.
**Warning signs:** Steps appearing in wrong order in the workflow diagram.

### Pitfall 4: team_engagement Merge Creates New Section Instead of Merging
**What goes wrong:** Merge button calls approve with `action: "merge"` but the approve route
hits the `default` case and inserts a new history row instead of updating the section.
**Why it happens:** `field` is `'team_engagement'` but `entity_match` (section name) is needed
to locate the existing row. If `entity_match` is missing from the POST body, the merge cannot proceed.
**How to avoid:** Validate in the Zod schema that when `action === 'merge'`, `entity_match` is required.
Return a 400 if missing.
**Warning signs:** New `teamEngagementSections` rows created with duplicate names.

### Pitfall 5: suggested_position JSON Parsing Failure
**What goes wrong:** `suggested_position` stored as a JSON string in DB, parsed with `JSON.parse()`,
throws if malformed.
**Why it happens:** Claude may return a malformed JSON value for `suggested_position`.
**How to avoid:** Wrap `JSON.parse(item.suggested_position)` in a try/catch; default to `undefined`
(insert at end) if parsing fails.
**Warning signs:** 500 errors on workflow_step merge approvals.

### Pitfall 6: Drizzle `sql` Template Tag Import
**What goes wrong:** `sql` is not imported from `drizzle-orm` in `approve/route.ts`, causing a TS error.
**Why it happens:** Current imports only use `eq` and `and` from `drizzle-orm`.
**How to avoid:** Add `sql` to the import: `import { eq, and, sql } from 'drizzle-orm';`
**Warning signs:** TypeScript compile error on the sql template tag usage.

## Open Questions

1. **Should `onConflictDoUpdate` (upsert) be used instead of `onConflictDoNothing` for arch_node?**
   - What we know: The spec says "fix the bug" and the Phase 84 note says "silently skipping" is the goal.
   - What's unclear: Should a second approve of the same arch_node update the existing node's data?
   - Recommendation: Use `.onConflictDoNothing()` for the bug fix (matching Phase 84 spec intent). The
     merge flow (MERGE-05) handles enrichment explicitly via the Merge button.

2. **Should `suggested_position` resequence existing steps or just insert at a computed offset?**
   - What we know: Position gaps are acceptable; there's no unique constraint on `workflowSteps.position`.
   - What's unclear: If the UI renders steps strictly in position order, gaps could eventually cause
     display issues (e.g. step at position=0 and next at position=5 with a new one inserted at position=1).
   - Recommendation: Insert at `anchor.position + 1` without resequencing. Document the gap behavior.
     Display code should use `ORDER BY position ASC, id ASC` as a stable tiebreaker.

3. **Wave 0 test scope: should the onConflictDoNothing fix have its own test?**
   - What we know: The existing `approve.test.ts` has no test for duplicate arch_node approval.
   - Recommendation: Yes — add a RED test that calls the approve route twice with the same arch_node
     item and asserts the second call returns `approved: 1, errors: []` (not a 500). This test gates BUG-01.
